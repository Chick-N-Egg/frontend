# Plan: `backend-nest/` — servicio NestJS en paralelo al backend Python

## 0. Resumen de la decisión de reconciliación de modelos

Uso **PRODUCT_SPEC.md como fuente de nombres de entidades** (`Brief`, `Result`, `Attempt`) porque es el documento versionado en git con AC de producto, pero incorporo del `.mmd` los tres patrones arquitectónicos explícitos que pide:

1. **Value objects para campos compuestos** (no solo strings sueltos) — ej. `ScoreBreakdown` como VO en vez de tres columnas sueltas sin cohesión.
2. **Enums TypeScript reales** para todo campo cerrado (`Stage`, `ChannelType`, `Outcome`, `Source`), igual que el `.mmd` usa `Stage`/`Category`/`EngagementLevel`/`OutcomeStatus` como enums de primera clase.
3. **Interfaces de repositorio explícitas** (`BriefRepository`, `DiscoveryRepository`/`ResultRepository`, `AttemptRepository`, `ChannelMatcher`) inyectadas por token, con la implementación TypeORM detrás — esto traduce directamente `PlaybookRepository`/`MatchResultRepository`/`CommunityMatcher` del `.mmd`.

`Category` del `.mmd` (HEALTHTECH, B2B_SAAS, FINTECH, EDTECH, DEVELOPER_TOOLS, AI, GENERAL_STARTUP) **no se mantiene como enum rígido**: PRODUCT_SPEC.md pide `audience_segments` como array de strings libres extraídos por IA del texto natural del founder (más fiel al "no soy Apollo, no asumo ICP confirmado" que es el core insight del producto). Se pierde tipado fuerte de categoría, pero se gana fidelidad al spec oficial — trade-off explícito documentado en el modelo. `Stage` sí se mantiene como enum (`idea | mvp | early-traction`, valores de PRODUCT_SPEC, no los 4 del `.mmd` que son de otro naming más viejo del producto).

`Playbook`/`MatchResult` del `.mmd` colapsan en `Result` de PRODUCT_SPEC (que ya incluye score + `suggested_approach` + `draft_message` en una sola entidad, en vez de separar matching y playbook en dos tablas). `Outcome`/`OutcomeStatus` del `.mmd` se traducen a `Attempt.outcome` (enum `no_response|declined|interested|signed_up|paying`, con `revenue` opcional) — más rico que el `OutcomeStatus` de 4 valores del `.mmd` porque el spec de producto pide el funnel completo.

## 1. Modelo de dominio final

### `Brief`
```
id: uuid
raw_input: text
product_summary: text          // extraído por IA
audience_segments: string[]    // extraído por IA (jsonb column)
stage: Stage enum (idea | mvp | early_traction)
created_at: timestamptz
```

### `Result`
```
id: uuid
brief_id: fk -&gt; Brief
channel_type: ChannelType enum (discord | reddit | facebook_group | company | individual)
name: string
url: string | null
why_it_fits: text
reach_score: int (1-5)
receptiveness_score: int (1-5)
warmth_score: int (1-5)
confidence_total: numeric(4,2)   // persistido, no derivado en query — ver más abajo
source: ResultSource enum (verified_data | web_search | manual)
suggested_approach: text | null
draft_message: text | null
created_at: timestamptz
```

`confidence_total` se calcula server-side en el momento de creación/actualización del `Result` (no como columna generada de Postgres, para poder recalcularse cuando el "refinement loop" ajuste pesos en el futuro sin migración de esquema):

```
confidence_total = reach_score*0.3 + receptiveness_score*0.4 + warmth_score*0.3
```

Esta fórmula vive en **un único lugar**: `ScoringService.computeConfidence(scores: ScoreBreakdown): number`, un value object puro (sin dependencias de NestJS/DB) para que sea trivial testear con Jest y reemplazar cuando llegue el "refinement" real basado en `Attempt` histórico.

### `Attempt`
```
id: uuid
result_id: fk -&gt; Result
message_sent: text
outcome: AttemptOutcome enum (no_response | declined | interested | signed_up | paying)
revenue: numeric(10,2) | null   // solo relevante si outcome = paying, validado en DTO
notes: text | null
logged_at: timestamptz
```

### Traducción del patrón repository-interface del `.mmd` a NestJS

El `.mmd` pide interfaces explícitas (`PlaybookRepository`, `MatchResultRepository`, `CommunityMatcher`) en vez de acceso directo a ORM desde los servicios. En NestJS esto se hace con **tokens de inyección + interfaces TS + adaptador TypeORM**, patrón puertos-y-adaptadores:

```typescript
// domain/ports/brief.repository.ts
export interface BriefRepository {
  findById(id: string): Promise&lt;Brief | null&gt;;
  save(brief: Brief): Promise&lt;Brief&gt;;
}
export const BRIEF_REPOSITORY = Symbol('BRIEF_REPOSITORY');

// domain/ports/result.repository.ts
export interface ResultRepository {
  findById(id: string): Promise&lt;Result | null&gt;;
  findByBriefId(briefId: string): Promise&lt;Result[]&gt;;
  saveMany(results: Result[]): Promise&lt;Result[]&gt;;
}
export const RESULT_REPOSITORY = Symbol('RESULT_REPOSITORY');

// domain/ports/attempt.repository.ts
export interface AttemptRepository {
  save(attempt: Attempt): Promise&lt;Attempt&gt;;
  findAll(): Promise&lt;Attempt[]&gt;;         // usado por DashboardService
  findByResultId(resultId: string): Promise&lt;Attempt[]&gt;;
}
export const ATTEMPT_REPOSITORY = Symbol('ATTEMPT_REPOSITORY');

// domain/ports/channel-matcher.ts  (equivalente a CommunityMatcher del .mmd)
export interface ChannelMatcher {
  match(brief: Brief, catalog: ChannelCandidate[]): Promise&lt;ScoredCandidate[]&gt;;
}
export const CHANNEL_MATCHER = Symbol('CHANNEL_MATCHER');
```

Los adaptadores TypeORM (`TypeOrmBriefRepository`, `TypeOrmResultRepository`, `TypeOrmAttemptRepository`) implementan estas interfaces y se registran así en cada módulo:

```typescript
providers: [
  { provide: BRIEF_REPOSITORY, useClass: TypeOrmBriefRepository },
]
```

`OpenAiChannelMatcher implements ChannelMatcher` es el único punto donde se llama a OpenAI para discovery+scoring — reemplaza el "Cala" ficticio del prototipo. Los servicios de aplicación (`BriefService`, `DiscoveryService`, etc.) **solo dependen de las interfaces**, nunca de `Repository&lt;Entity&gt;` de TypeORM directamente ni del SDK de OpenAI directamente. Esto es justo lo que pide el `.mmd` y además hace testeable cada servicio con mocks triviales.

## 2. Stack técnico

| Decisión | Elección | Justificación |
|---|---|---|
| NestJS | `^10.x` (última estable a la fecha) | LTS de Node 20 compatible, `@nestjs/cli` para scaffolding |
| ORM | **TypeORM** (no Prisma) | El patrón repository-interface del `.mmd` encaja de forma nativa con `Repository&lt;T&gt;` de TypeORM inyectado dentro de un adaptador; Prisma genera un cliente global tipado que empuja hacia acceso directo desde servicios y hace más forzado ocultarlo detrás de una interfaz de dominio propia. TypeORM además tiene decoradores de entidad que mapean 1:1 con las clases del `.mmd` (`@Entity`, `@Column`, enums nativos de Postgres vía `enum:` en la columna). |
| Base de datos | **PostgreSQL** | El prototipo (`REDACTED-tech-arch.html`) ya la sugiere, y el dashboard con funnel/agregaciones se beneficia de SQL real. Imagen Docker: **`postgres:16-bookworm`** (variante Debian explícita, no `postgres:16-alpine` ni el tag `postgres:16` a secas que en Docker Hub apunta a Debian pero sin dejarlo explícito) — consistente con el patrón de comentarios explícitos ya usado en `backend/Dockerfile` y `frontend/Dockerfile` ("X es Debian-based, no alpine"). |
| Validación | **class-validator + class-transformer** | Es el paquete estándar/first-party de Nest (`ValidationPipe` global), se integra directo con DTOs decorados, evita añadir una dependencia de validación paralela (Zod) cuando Nest ya trae su propio patrón idiomático. |
| Cliente OpenAI | paquete `openai` (Node SDK oficial) | Mismo proveedor y mismo patrón que `backend/main.py` (`response_format: { type: "json_object" }`), reutilizando la misma `OPENAI_API_KEY`. |
| Config | `@nestjs/config` con `.env` propio (`backend-nest/.env`, gitignored igual que `backend/.env`) | Aislado del `.env` de Python; evita acoplar ciclos de vida de configuración entre los dos backends. |

### `channel-catalog` — nota sobre el catálogo estático

Esto es una **limitación conocida y documentada explícitamente** en un comentario en `channel-catalog.service.ts` y en el `.env.example`: PRODUCT_SPEC.md pide "datos verificados/sourced" reales (el "Cala" ficticio), pero no existe integración real disponible, así que el MVP de NestJS usa el mismo catálogo estático que ya usa el backend Python, con `source = 'verified_data'` marcado honestamente solo para las entradas que vienen de este catálogo curado a mano, y `web_search`/`manual` reservados para cuando OpenAI complemente con candidatos fuera del catálogo (companies/individuals, que no existen en `communities.json`).

## 4. Endpoints

| Método | Ruta | Body / Query | Descripción |
|---|---|---|---|
| `POST` | `/briefs` | `{ raw_input }` | Paso 1: llama a `brief-extractor` (OpenAI), devuelve `{ product_summary, audience_segments, stage, clarifying_question }` y persiste el `Brief` |
| `PATCH` | `/briefs/:id` | `{ product_summary?, audience_segments?, stage? }` | Edición de los chips antes de confirmar (spec pide "editable chips") |
| `GET` | `/briefs/:id` | — | Recuperar un brief |
| `POST` | `/briefs/:id/discover` | `{}` | Pasos 2-3: `DiscoveryService` cruza `audience_segments` contra `channel_candidate` + completa con OpenAI, calcula `confidence_total` por `ScoringService`, persiste N `Result`, devuelve ordenado desc con el top marcado `is_best_shot: true` |
| `GET` | `/briefs/:id/results` | — | Lista de resultados ya generados para un brief |
| `POST` | `/results/:id/outreach` | `{}` | Paso 4: genera `suggested_approach` + `draft_message`, actualiza el `Result` |
| `POST` | `/results/:id/attempts` | `{ message_sent, outcome, revenue?, notes? }` | Paso 5: loguea un `Attempt` |
| `GET` | `/attempts` | `?resultId=` opcional | Listado (usado por "recent attempts log" del dashboard) |
| `GET` | `/dashboard` | — | KPIs, growth over time, funnel, performance por channel_type, recent attempts, `refinement_insight` (null si &lt;3 attempts) |
| `GET` | `/health` | — | Healthcheck simple para Docker/compose |

Todos bajo un prefijo global `app.setGlobalPrefix('v1')` o sin prefijo pero **nunca `/api`**, para no chocar conceptualmente ni operativamente con el proxy `/api` del frontend actual (que sigue apuntando solo al backend Python).

## 5. Dockerfile + docker-compose

### `backend-nest/Dockerfile` (multi-stage, Debian, mismo espíritu que `backend/Dockerfile`)

```dockerfile
# caddy:2 es Debian (bookworm) por defecto — se usa solo para copiar el binario.
FROM caddy:2 AS caddy

# node:20-bookworm-slim es Debian 12, no alpine — build stage con devDependencies.
FROM node:20-bookworm-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY tsconfig*.json nest-cli.json ./
COPY src ./src
RUN npm run build

# node:20-bookworm-slim — runtime stage, solo deps de producción.
FROM node:20-bookworm-slim
RUN apt-get update \
    &amp;&amp; apt-get install -y --no-install-recommends ca-certificates \
    &amp;&amp; rm -rf /var/lib/apt/lists/*
COPY --from=caddy /usr/bin/caddy /usr/bin/caddy
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
COPY src/channel-catalog/seed/communities.seed.json ./dist/channel-catalog/seed/communities.seed.json
COPY Caddyfile /etc/caddy/Caddyfile
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
EXPOSE 80
ENTRYPOINT ["/entrypoint.sh"]
```

`Caddyfile` idéntico en espíritu al de `backend/`, reverse-proxeando `:80 -&gt; 127.0.0.1:3000` (puerto interno Nest). `entrypoint.sh` calca el patrón de `backend/entrypoint.sh` (lanza `node dist/main.js` + `caddy run`, `wait -n`, propagación de señales) — opcionalmente corriendo `npm run migration:run` antes de arrancar Nest.

## 6. Plan de verificación end-to-end

```bash
# 1. Levantar solo el servicio nuevo + su DB (sin afectar backend/frontend existentes)
docker compose up -d --build postgres-nest backend-nest

# 2. Healthcheck
curl -s http://localhost:8081/health

# 3. Crear Brief (paso 1)
BRIEF_ID=$(curl -s -X POST http://localhost:8081/briefs \
  -H 'Content-Type: application/json' \
  -d '{"raw_input":"Estamos construyendo una app para que founders indie encuentren su primer cliente en comunidades online."}' \
  | jq -r '.id')

# 4. (Opcional) editar chips
curl -s -X PATCH http://localhost:8081/briefs/$BRIEF_ID \
  -H 'Content-Type: application/json' \
  -d '{"stage":"mvp"}'

# 5. Discovery + scoring (pasos 2-3) → genera Results rankeados
curl -s -X POST http://localhost:8081/briefs/$BRIEF_ID/discover | jq

RESULT_ID=$(curl -s http://localhost:8081/briefs/$BRIEF_ID/results | jq -r '.[0].id')

# 6. Generar outreach kit (paso 4)
curl -s -X POST http://localhost:8081/results/$RESULT_ID/outreach | jq

# 7. Loguear un Attempt con outcome (paso 5)
curl -s -X POST http://localhost:8081/results/$RESULT_ID/attempts \
  -H 'Content-Type: application/json' \
  -d '{"message_sent":"Hola! vi que...", "outcome":"signed_up"}' | jq

# 8. Dashboard: confirmar que el Attempt se refleja en KPIs/funnel
curl -s http://localhost:8081/dashboard | jq
```

Criterio de éxito: el `dashboard` en el paso 8 muestra `total_attempts: 1`, `funnel.signed_up: 1`, y `refinement_insight: null` (porque el spec exige mínimo 3 attempts) — repetir el paso 7 dos veces más con outcomes distintos para verificar que `refinement_insight` deja de ser null a partir del tercer `Attempt`, cumpliendo el AC explícito de PRODUCT_SPEC.md ("generated once there's enough logged data, 3+ attempts minimum").

Adicionalmente, verificar que **no se rompe nada existente**: `curl http://localhost:8080/api/dashboard-stats` (frontend → backend Python, puerto 8080 ya establecido) debe seguir funcionando exactamente igual, confirmando aislamiento total entre ambos backends.
